# Выбор и настройка мониторинга в системе

## Анализ системы

На C4-диаграмме заказ проходит через десять контейнеров, и каждый из них работает в единственном экземпляре. Отказ или перегрузка любого останавливает свой участок пути заказа, поэтому мониторинг нужен для каждого контейнера.

| Контейнер | Роль в пути заказа | Что важно видеть |
| :- | :- | :- |
| Internet Shop | Оформление заказа покупателем, загрузка модели, конструктор | Поведение посетителей и конверсию уже показывает Яндекс Метрика. Технические проблемы видны по Shop API |
| Shop API | Каталог, приём заказов и 3D-моделей от покупателей | Поток запросов, ошибки, время ответа, объём загружаемых моделей |
| Shop DB | Заказы с точки зрения покупателя, общая база магазина и CRM | Подключения обоих приложений, заполнение диска, нагрузка |
| CRM, CRM API | Передача заказов магазина в MES, подтверждение заказов продавцами, закрытие заказов | Ошибки и время ответа, публикация и обработка сообщений |
| RabbitMQ | Единственный канал между CRM и MES. Только через него заказ партнёра попадает в CRM | Сообщения, которые копятся, не подтверждаются или уходят в DLX, наличие потребителей у очередей, ресурсы брокера |
| MES API | Расчёт стоимости, API для партнёров, дашборд операторов | Запросы операторов и партнёров, длительность и число расчётов, загрузка CPU и памяти |
| MES | Интерфейс операторов | Время ответа дашборда на стороне MES API |
| MES db | Заказы, назначения и статусы в производстве | Подключения, заполнение диска, медленные запросы дашборда |
| 3d files storage | 3D-модели заказов | Рост объёма |

Кроме контейнеров, нужен взгляд на сам процесс: сколько заказов на каждом этапе и как долго они там находятся. Ни один контейнер по отдельности на этот вопрос не отвечает, поэтому к техническим метрикам добавляются бизнес-метрики процесса заказа.

## Мотивация

Сейчас о проблемах с заказами компания узнаёт от клиентов, иногда через несколько месяцев после оформления. Яндекс Метрика показывает поведение посетителей сайта, но заказы партнёров идут через API и в неё не попадают. Не видно и того, что происходит с заказом после оформления: расчёт, передача между системами, производство.

| Проблема бизнеса | Что даёт мониторинг |
| :- | :- |
| Заказы партнёров теряются, компания теряет контракты | Оповещение о каждом сообщении, ушедшем в DLX, и о расхождении заказов между MES и CRM. Менеджер узнаёт о проблеме раньше партнёра и успевает её решить |
| Заказы выполняются месяцами вместо трёх недель | Видно, на каком этапе копятся заказы и сколько они там ждут. Появляется возможность задать норматив на каждый этап и контролировать его |
| Операторы жалуются на медленный MES | Время загрузки дашборда и загрузка MES API в цифрах. Видно, помогла ли доработка |
| Каждый месяц заказов на 100 больше, растёт поток от партнёров | Прогноз, когда закончатся ресурсы. Мощности добавляются заранее, а не после аварии |
| Нужно решить, во что вкладывать ресурсы команды | Значения до и после каждого изменения из плана задания 1. Бизнес видит, что получил за вложенное время |
| Договорённости с партнёрами | Фактическая доступность API и время расчёта по каждому партнёру. Это аргумент в переговорах и основа для SLA |
| Разбор инцидентов занимает много времени | Метрики сразу показывают, в какой системе и с какого момента начались проблемы, разработчики не ищут причину вслепую |

Внедрение стоит два-три спринта работы DevOps-инженера и небольшие доработки кода приложений. Инструменты с открытой лицензией, из инфраструктуры нужна одна виртуальная машина для prod и одна небольшая для тестовых окружений. Это дешевле одного потерянного крупного контракта.

## Выбор подхода к мониторингу

- **RED** (Rate, Errors, Duration) описывает сервисы, которые обрабатывают запросы: сколько запросов, сколько ошибок, сколько времени занимает ответ.
- **USE** (Utilization, Saturation, Errors) описывает ресурсы: насколько ресурс занят, есть ли очередь к нему, есть ли ошибки.
- **Четыре золотых сигнала** (latency, traffic, errors, saturation) объединяют оба взгляда: RED плюс насыщенность.

| Часть системы | Подход | Почему |
| :- | :- | :- |
| Shop API, CRM API | RED | Сервисы обрабатывают запросы покупателей, продавцов и обработчиков сообщений. Пользователь чувствует скорость и ошибки, а нагрузку показывает частота запросов. Ресурсы их виртуальных машин смотрим по USE |
| MES API | Четыре золотых сигнала | Кроме запросов операторов и партнёров, MES API выполняет расчёт стоимости, который упирается в CPU и память. Главный сигнал здесь насыщенность: загрузка процессора, число одновременных расчётов, ожидание расчёта. RED не покажет насыщение, а USE не покажет, как его чувствуют операторы и партнёры |
| RabbitMQ | USE | Брокер - это ресурс, через который проходят все сообщения между CRM и MES. Утилизация: память, диск и подключения относительно лимитов. Насыщенность: сообщения, которые копятся в очередях. Ошибки: письма в DLX и сообщения без маршрута |
| Shop DB, MES db | USE | Утилизация: CPU, память, диск, подключения. Насыщенность: ожидание подключений и блокировок. Ошибки: отказы в подключении, deadlock |
| Виртуальные машины | USE | CPU, память, диск, сеть |
| 3d files storage | USE, только утилизация | Хранилище не ограничено по объёму, важен рост объёма для прогноза затрат |
| Процесс заказа | Бизнес-метрики процесса | Ни один из трёх подходов не отвечает на вопрос, где находится заказ. Для процесса используем тот же принцип, что в RED: поток заказов через каждый этап, отказы и время на этапе |

## Метрики

Каждый ряд получает ярлыки `env` (dev, release, prod) и `service` из настроек сбора, в таблицах они не указываются. В ярлыки не попадают идентификатор пользователя, номер заказа, полный URL и текст ошибки: у них неограниченное число значений, Prometheus создаёт ряд на каждое значение и перестаёт справляться. Путь конкретного заказа ищется в логах и трейсах, а не в метриках.

### Метрики из списка

**RabbitMQ**

| Метрика | Зачем | Ярлыки |
| :- | :- | :- |
| Number of dead-letter-exchange letters in RabbitMQ | Каждое письмо в DLX - необработанное сообщение о заказе: заказ партнёра не создан в CRM или смена статуса не дошла до другой системы. Главный сигнал о потере заказов, оповещение при любом ненулевом значении | `queue` (исходная очередь), `reason` (rejected, expired, maxlen, delivery_limit), `message_type` (создание заказа, смена статуса, результат расчёта) |
| Number of message in flight in RabbitMQ | Сообщения, которые брокер принял, но потребитель ещё не обработал. Рост означает, что потребитель не справляется или завис, а заказы в это время стоят | `queue`, `state` (ready - ждут потребителя, unacked - выданы и не подтверждены) |

**API**

| Метрика | Зачем | Ярлыки |
| :- | :- | :- |
| Number of requests (RPS) for internet shop API | Поток запросов покупателей, основа для оценки нагрузки и её роста месяц к месяцу. Резкий провал говорит о недоступности сайта | `method`, `route` (шаблон маршрута, например `/orders/{id}`), `status` |
| Number of requests (RPS) for CRM API | Нагрузка от продавцов и от обработчиков сообщений | `method`, `route`, `status` |
| Number of requests (RPS) for MES API | Нагрузка от операторов и партнёров. Показывает долю запросов партнёров и то, как часто операторы обновляют дашборд | `method`, `route`, `status`, `client` (mes-ui, partner-api) |
| Number of requests (RPS) per user for MES API | Считаем по партнёрам, а не по всем пользователям. Показывает, какой партнёр создаёт нагрузку. Нужна для квот и для разговора с партнёром раньше, чем он перегрузит систему | `partner_id`, `route`, `status`. Партнёров десятки, число значений ограничено |
| Response time (latency) for shop API | Скорость, которую чувствует покупатель. Собираем гистограмму и смотрим перцентили p50, p95, p99: среднее скрывает медленные запросы | `method`, `route`, `status` |
| Response time (latency) for CRM API | То же для продавцов и обработчиков сообщений | `method`, `route`, `status` |
| Response time (latency) for MES API | Время загрузки дашборда, главная жалоба операторов. Позволяет проверить эффект ускорения дашборда и кеширования | `method`, `route`, `status`, `client` |
| Number of HTTP 200 for shop API, CRM API, MES API | Не отдельная метрика, а срез счётчика запросов по ярлыку `status`. Доля успешных ответов от всех запросов показывает доступность API | `route`, `status` |
| Number of HTTP 500 for shop API, CRM API, MES API | Ошибки сервера. Считаем все ответы 5xx, а не только 500: коды 502, 503 и 504 означают недоступность или таймаут. Для MES API отдельно смотрим 4xx по партнёрам, это ошибки интеграции на их стороне | `method`, `route`, `status`, для MES API ещё `client` и `partner_id` |
| Kb tranferred (received) for shop API | Объём загружаемых 3D-моделей. Время расчёта зависит от сложности модели, и рост объёма загрузок заранее предупреждает о росте нагрузки на расчёт | `route` |
| Kb tranferred (received) for MES API | То же для моделей, которые присылают партнёры | `route`, `partner_id` |

**Ресурсы приложений**

| Метрика | Зачем | Ярлыки |
| :- | :- | :- |
| CPU % for shop API, CPU % for CRM API | Загрузка виртуальных машин приложений. Нужна для планирования ресурсов и объясняет рост времени ответа | `instance`, `mode` (user, system, iowait) |
| CPU % for MES API | Расчёт стоимости упирается в процессор. Высокая загрузка означает, что расчёты и запросы операторов конкурируют за CPU | `instance`, `mode` |
| Memory Utilisation for shop API, Memory Utilisation for CRM API | Нехватка памяти JVM приводит к долгим паузам сборщика мусора и падению приложения | `instance`, `area` (heap, nonheap) |
| Memory Utilisation for MES API | На время расчёта модель загружается в память, детализированная модель может занять её целиком. Падение MES API прерывает все идущие расчёты | `instance`, `generation` (поколение сборщика мусора .NET) |

**Базы данных и хранилище**

| Метрика | Зачем | Ярлыки |
| :- | :- | :- |
| Memory Utilisation for shop db instance | При нехватке памяти данные вытесняются из кеша PostgreSQL, запросы идут на диск и замедляются | `host` |
| Memory Utilisation for MES db instance | То же, прежде всего для запросов дашборда | `host` |
| Number of connections for shop db instance | С Shop DB работают два приложения. Подключения по приложениям показывают, кто занимает соединения. Приближение к max_connections означает отказ в новых подключениях | `application` (shop-api, crm-api), `state` (active, idle, idle in transaction) |
| Number of connections for MES db instance | То же для MES API | `application`, `state` |
| Size of shop db instance | При полном диске база перестаёт принимать запись, и заказы не сохраняются | `host`, `database` |
| Size of MES db instance | То же. MES db растёт с каждым заказом, архивации нет | `host`, `database` |
| Size of S3 storage | Рост объёма моделей для прогноза затрат и настройки политики хранения. Меняется медленно, собираем раз в час | `bucket` |

**Не отслеживаем**

| Метрика | Почему |
| :- | :- |
| Number of requests (RPS) per user for internet shop API | Покупателей много, ряд на каждого перегрузит Prometheus. Всплески от одного клиента ищем в логах, защищаемся лимитами на балансировщике |
| Number of requests (RPS) per user for CRM API | Продавцов немного, их нагрузка видна в общем RPS CRM API |
| Number of requests (RPS) per user for MES API по операторам | Нагрузку операторов показывает RPS маршрута дашборда. По пользователям считаем только партнёров |
| Number of simultanious sessions for shop API, CRM API, MES API | Посетителей сайта показывает Яндекс Метрика. У CRM и MES пользователей немного и их число известно, нагрузку они создают запросами, которые видны в RPS |
| Kb tranferred (received) for CRM API | CRM API принимает небольшие JSON-запросы, объём не влияет на решения |
| Kb provided (sent) for shop API, CRM API, MES API | Ответы API - JSON небольшого размера. Сетевой трафик виртуальных машин и так виден в метриках ресурсов |

| `price_calculation_wait_seconds` | Сколько заказ ждал начала расчёта. Прямо показывает, успевает ли MES за потоком заказов | `channel` |

**Обмен сообщениями**

| Метрика | Зачем | Ярлыки |
| :- | :- | :- |
| `messages_published_total`, `messages_consumed_total` | Публикация и обработка сообщений со стороны приложений. Расхождение между опубликованными и обработанными сообщениями показывает потерю ещё до DLX, например если публикация не дошла до брокера | `system`, `exchange` или `queue`, `message_type`, `result` (ok, error, retry) |

**Насыщенность приложений и баз**

| Метрика | Зачем | Ярлыки |
| :- | :- | :- |
| Активные и ожидающие подключения в пуле приложения (HikariCP, пул Npgsql) | Ожидающие подключения появляются раньше, чем растёт время ответа | `pool` |
| Занятые потоки обработки запросов (Tomcat) и очередь пула потоков .NET | Долгие расчёты занимают потоки MES API, и запросы операторов ждут в очереди | `instance` |
| Паузы сборщика мусора JVM и .NET | Объясняют всплески времени ответа | `instance` |
| Время выполнения запросов к базе (pg_stat_statements) | Находит медленные запросы, прежде всего запрос списка заказов на дашборде. Берём 20 самых тяжёлых запросов | `database`, `queryid` |
| Блокировки и deadlock | Два приложения пишут в одну Shop DB | `database` |
| Свободное место и задержки диска виртуальных машин и баз | Логи и сообщения RabbitMQ пишутся на диск, база при полном диске перестаёт принимать запись | `host`, `mountpoint` |

**Доступность снаружи**

| Метрика | Зачем | Ярлыки |
| :- | :- | :- |
| Внешняя проверка доступности | Магазин, CRM, MES и API для партнёров отвечают снаружи. Проверка ловит проблемы, которые не видны изнутри: DNS, сертификаты, сеть | `target` |
| Срок действия TLS-сертификатов | Просроченный сертификат останавливает приём заказов от партнёров | `target` |

## План действий

### Инфраструктура мониторинга

1. Создать виртуальную машину monitoring-prod в Yandex Cloud (4 vCPU, 8 ГБ RAM, SSD 200 ГБ) в сети prod-окружения. Развернуть на ней Prometheus как time-series базу с хранением 13 месяцев, чтобы сравнивать нагрузку месяц к месяцу.
2. Для dev и release развернуть отдельный Prometheus с хранением 15 дней. Метрики тестовых окружений не смешиваются с продовыми и не вызывают оповещений.
3. Развернуть Grafana с источниками данных обоих Prometheus. Роли: просмотр для продакт-менеджера и менеджеров по продажам, редактирование для инженеров.
4. Развернуть Alertmanager. Критичные оповещения уходят звонком и сообщением дежурному, предупреждения в чат команды и тикетом в трекер, бизнес-оповещения в чат продавцов.
5. Настроить Watchdog: постоянно активный алерт отправляется во внешний сервис, и если он перестал приходить, значит, не работает сам мониторинг.
6. Открыть эндпоинты метрик приложений и экспортеров только для машины мониторинга через группы безопасности.
7. Хранить конфигурацию Prometheus, правила алертов и дашборды Grafana в git и выкатывать через CI.

### Сбор метрик инфраструктуры

8. Установить node_exporter на виртуальные машины Shop API, CRM API, MES API и RabbitMQ.
9. Включить в RabbitMQ плагин rabbitmq_prometheus с метриками по каждой очереди. Настроить DLX для всех рабочих очередей (часть инициативы И1), иначе необработанные сообщения теряются и считать нечего. ## Показатели насыщенности

Показатели выбраны по узким местам пути заказа: MES API, где расчёт конкурирует с запросами операторов и партнёров, RabbitMQ как единственный канал между CRM и MES, и две базы на одном инстансе каждая. Для каждого ресурса берётся то, что заканчивается первым и после чего система не замедляется, а отказывает: процессор и память под расчётом, подключения к базе, диск, память брокера. Там, где ресурс считать неудобно, насыщенность измеряется ожиданием: сколько заказ ждёт расчёта, сколько запрос ждёт подключения или потока. Ожидание прямо показывает, чувствуют ли насыщение покупатели, партнёры и операторы.

Все пороги срабатывают, только если значение держится заданное время: короткие пики нормальны, а алерт на каждый пик приучает команду игнорировать оповещения.
