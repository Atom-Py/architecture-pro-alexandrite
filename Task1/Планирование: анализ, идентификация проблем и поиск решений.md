# Планирование: анализ, идентификация проблем и поиск решений

## Как сейчас проходит заказ

Заказ проходит через три приложения и две базы данных, статусы меняются в каждой системе.

1. Покупатель оформляет заказ в интернет-магазине. Shop API сохраняет заказ в Shop DB, а 3D-модель в S3-хранилище. Статусы INITIATED, FILE_UPLOADED, SUBMITTED.
2. Shop API с очередью не связан, поэтому заказ попадает в MES через CRM: CRM API читает его из общей Shop DB и публикует сообщение в RabbitMQ.
3. MES API берёт модель из S3 и рассчитывает стоимость. Заказ получает статус PRICE_CALCULATED, результат уходит в CRM через RabbitMQ.
4. Продавец подтверждает заказ в CRM (MANUFACTURING_APPROVED), подтверждение уходит в MES.
5. Оператор берёт заказ в работу в MES и ведёт его по статусам MANUFACTURING_STARTED, MANUFACTURING_COMPLETED, PACKAGING, SHIPPED. Каждое изменение отправляется в CRM.
6. CRM закрывает заказ (CLOSED) по сообщению транспортной компании или вручную.

Заказ партнёра начинается сразу с расчёта: партнёр отправляет модель в MES API, MES сохраняет её в S3 и считает стоимость, а заказ в CRM создаётся по сообщению из MES. Если сообщение не дошло, CRM о заказе не знает и продавцу нечего подтверждать.

## Проблемы

### Существующие

| № | Проблема | Причина | Последствия |
| :-: | :- | :- | :- |
| П1 | Расчёт стоимости тормозит весь MES | Расчёт идёт внутри MES API на единственном инстансе и занимает от 2-3 до 30 минут. В том же процессе работают интерфейс операторов и API для партнёров. Очереди заданий и приоритетов нет, сложная модель занимает ресурсы на полчаса наравне с простыми | Когда заказов приходит больше, чем MES успевает посчитать, они копятся в статусе SUBMITTED, и с ростом потока ожидание только увеличивается. Страдают все каналы сразу: покупатели, партнёры и операторы |
| П2 | Заказы партнёров теряются | Заказ партнёра появляется в CRM только по сообщению из MES. Сообщения между MES и CRM теряются: в интеграции нет подтверждений публикации и обработки, повторов, очереди недоставленных сообщений (DLX) и защиты от дублей. Запись в MES db и отправка сообщения не атомарны | Заказ есть в MES, но его нет в CRM: продавец его не видит и не подтверждает, в производство он не попадает. Партнёры ежедневно жалуются, компания уже потеряла несколько крупных контрактов |
| П3 | Внешний API не защищён от перегрузки | Партнёры обращаются напрямую в MES API, лимитов и квот нет. Трафик партнёров конкурирует с заказами магазина и с работой операторов за один инстанс. Узнать статус заказа через API партнёр не может | После открытия API систему завалило заказами, и сроки выросли во всех каналах, в том числе в B2C. О судьбе заказа партнёры узнают только от менеджеров |
| П4 | Неизвестно, где находится заказ | Статусы разнесены по трём системам и двум базам, единого источника нет. Мониторинга, централизованных логов и трейсинга нет, Яндекс Метрика видит только сайт и не видит заказы через API | О зависших заказах компания узнаёт из жалоб клиентов, иногда через несколько месяцев. Разбор каждого случая занимает у разработчиков и поддержки много времени |
| П5 | Медленный дашборд MES | Список заказов читается из единственного инстанса MES db, который одновременно принимает запись расчётов и статусов. Операторы постоянно обновляют страницу, чтобы первыми увидеть новый заказ, и каждый раз выполняется тяжёлый запрос к растущей таблице. Фильтр и пагинация уменьшили объём ответа, но не стоимость запроса: сортировка по дате и OFFSET-пагинация по-прежнему проходят по большой выборке, а сам MES API занят расчётами | Операторы долго ждут страницу и не успевают брать новые заказы. Это бьёт по их вознаграждению и задерживает запуск заказов в производство |
| П6 | Ручные этапы без контроля сроков | Заказ ждёт подтверждения продавца в CRM, а затем выбора оператором в MES. Нормативов времени на этапах и напоминаний нет, операторы берут заказы по своему выбору | При росте потока заказы незаметно копятся на ручных этапах, обещанный срок в три недели никто не отслеживает |
| П7 | Долгие релизы | E2E-сценарии прогоняет вручную один QA-инженер, баги уровня high и highest блокируют релиз, в release и prod выкладывают вручную | Задержка релиза уже больше месяца. Исправления проблем с заказами доходят до пользователей так же медленно |
| П8 | Один разработчик на MES | В MES сосредоточены главные проблемы, а работает с ним один C#-разработчик. Фронтенд MES написан на React, фронтенд-инженеры пишут на Vue, React частично знает только один из них | Все доработки MES выстраиваются в очередь к одному человеку, его отпуск или уход останавливает работы |

### Потенциальные

| № | Проблема | Причина | Последствия |
| :-: | :- | :- | :- |
| П9 | Нет отказоустойчивости | У каждого приложения один инстанс, у каждой базы один инстанс на чтение и запись, брокер сообщений тоже один | Сбой любой виртуальной машины останавливает свою часть процесса. Ручной деплой на единственный инстанс означает простой, перезапуск MES API прерывает идущие расчёты |
| П10 | Рост нагрузки упрётся в вертикальное масштабирование | Каждый месяц заказов на 100 больше, поток от партнёров растёт отдельно. Приложения и базы масштабируются только увеличением виртуальной машины | Через несколько месяцев ресурсов не хватит даже после оптимизаций. Производство готово к двукратному росту, но будет простаивать из-за IT |
| П11 | Общая база магазина и CRM | CRM API напрямую читает и пишет Shop DB и узнаёт о новых заказах из чужой базы | Изменение схемы в магазине ломает CRM, долгие запросы одной системы тормозят другую, системы нельзя масштабировать и выпускать независимо |
| П12 | Гонка при взятии заказа | Операторам платят за взятые заказы, при медленной странице несколько операторов пытаются взять один и тот же заказ одновременно | Двойное назначение, споры о вознаграждении, повторная работа |
| П13 | Рост хранилищ | Детализированные 3D-модели от покупателей и партнёров копятся в S3, MES db растёт без архивации закрытых заказов | Растёт стоимость хранения, замедляются запросы и резервное копирование |
| П14 | Один DevOps-инженер | Мониторинг, логирование, трейсинг, кластеризация, автомасштабирование и переезд в Kubernetes ложатся на одного человека | Инфраструктурные задачи становятся узким местом всего плана |

## Приоритеты

Критерии, по которым расставлены приоритеты:

1. Влияние на деньги и клиентов. Потеря контрактов и срыв сроков важнее внутренних неудобств.
2. Устраняет ли инициатива причину проблемы или только её следствие.
3. Трудоёмкость и исполнители. В команде один C#-разработчик и один DevOps-инженер, поэтому работы распределены по потокам так, чтобы не стоять в очереди к одному человеку.
4. Зависимости. Без метрик нельзя проверить эффект остальных изменений, автомасштабирование воркеров требует метрики длины очереди.

| Приоритет | Инициатива | Обоснование | Трудоёмкость | Исполнители |
| :-: | :- | :- | :- | :- |
| 1 | И1. Гарантированная доставка сообщений и сверка заказов | Прямая причина потери заказов партнёров и контрактов. Поиск и восстановление потерянных заказов дают эффект уже в первом спринте | 2-3 спринта | Java- и C#-разработчики |

### Ход рассуждений

Производство справляется с потоком и готово к двукратному росту, значит сроки срываются до цеха: заказ долго ждёт расчёта, теряется между системами или стоит на ручном этапе. Эти три причины напрямую стоят компании денег, поэтому инициативы против них идут первыми. Остальные проблемы либо усиливают их (один инстанс, общая база, долгие релизы), либо мешают их увидеть (нет мониторинга, логов и трейсинга).

Внутри первой группы порядок задан ценой промедления. Потеря заказов партнёров уже стоила нескольких крупных контрактов, а часть потерянных заказов можно найти и восстановить в первом спринте, поэтому И1 первая. Асинхронный расчёт даёт наибольший эффект, но это самая крупная работа, поэтому она начинается одновременно с И1 и занимает первые три месяца. Мониторинг почти целиком делает DevOps-инженер, он не отнимает время у разработчиков и нужен раньше остальных изменений: без исходных цифр нельзя показать, что стало лучше, а автомасштабирование воркеров опирается на длину очереди.

Найм и автоматизация тестирования стоят высоко, хотя архитектуру не меняют. Все инициативы по MES упираются в одного C#-разработчика, а любое исправление сейчас доходит до продакшна больше месяца. Автоматизацию ведёт QA-инженер, это отдельный поток, который не конкурирует с разработкой.

Шлюз для партнёров, ускорение дашборда и контроль сроков этапов опираются на результаты первой волны. Асинхронный контракт шлюза использует очередь расчётов, кеш дашборда имеет смысл после того, как MES API перестанет считать стоимость, контроль сроков строится на метриках времени в статусе. Быстрые части этих инициатив, лимиты на шлюзе, индексы и keyset-пагинацию, можно сделать в первые спринты.

Трейсинг и логирование требуют доработки всех трёх систем, поэтому идут после мониторинга, когда основные узкие места уже закрыты. Масштабирование и отказоустойчивость нужны до следующего скачка нагрузки. Отказ от общей базы и переезд в Kubernetes долгие, в полгода входят только их первые этапы.

## Целевая архитектура через полгода

Система по-прежнему состоит из трёх приложений, но заказ проходит через неё предсказуемо: каждое сообщение либо обрабатывается, либо попадает в DLX с оповещением, расчёт стоимости не мешает остальной работе MES, а положение любого заказа видно без обращения к разработчикам.

| Часть системы | Сейчас | Через полгода |
| :- | :- | :- |
| Приём заказов партнёров | Напрямую в MES API без ограничений | Партнёрский API-шлюз: ключи, лимиты и квоты, идемпотентность, статус заказа по запросу и вебхуками |
| Расчёт стоимости | Внутри MES API на одном инстансе | Отдельные воркеры расчёта, очередь заданий в RabbitMQ с приоритетами, число воркеров меняется по длине очереди |
| MES API | Один инстанс, в котором идут расчёты, работа операторов и запросы партнёров | Два и более инстанса за балансировщиком, только приём заявок, статусы и дашборд |
| Дашборд MES | Тяжёлый запрос к базе при каждом обновлении | Индексы, keyset-пагинация, кеш списка заказов в Redis, новые заказы приходят через SSE |
| Обмен сообщениями | Один RabbitMQ, сообщения теряются | Кластер из трёх узлов, quorum queues, DLX с повторами, outbox и идемпотентные обработчики, регулярная сверка MES и CRM |
| Магазин и CRM | Общая Shop DB, CRM ищет новые заказы в чужой базе | Shop API публикует события заказа, CRM получает их из очереди. Общая база пока остаётся, её разделение следующий этап |
| Базы данных | Один инстанс на чтение и запись | Кластеры Managed PostgreSQL с репликой и автоматическим переключением, дашборд и отчёты читают с реплики |
| Наблюдаемость | Только Яндекс Метрика на сайте | Prometheus, Grafana и Alertmanager, OpenTelemetry и Jaeger, централизованные логи в OpenSearch. Дашборд прохождения заказов и алерты на зависшие заказы |
| Поставка | Ручной E2E, ручной деплой, релиз больше месяца | Автотесты в CI, автодеплой в release, деплой в prod без простоя, релиз раз в спринт |
| Инфраструктура | По одной виртуальной машине на приложение | Группы виртуальных машин с автомасштабированием, приложения в контейнерах, MVP в Kubernetes для последующего переезда |

## Три инициативы, если можно выполнить только три

1. **И1. Гарантированная доставка сообщений и сверка заказов.** Потерянные заказы партнёров уже стоили компании контрактов. Инициатива сравнительно недорогая: настройка RabbitMQ, outbox, идемпотентные обработчики и задача сверки. Первая же сверка даёт список заказов, которые потерялись сейчас, и их можно восстановить.
2. **И2. Асинхронный расчёт стоимости.** Это главная причина срыва сроков и медленной работы MES. Воркеры расчёта масштабируются горизонтально и выдерживают и ежемесячный прирост заказов, и поток от партнёров. Приоритеты очереди защищают заказы магазина от наплыва заявок партнёров, то есть частично закрывают задачу шлюза. MES API перестаёт выполнять расчёты, и дашборд операторов ускоряется без отдельной доработки.
3. **И4. Мониторинг и алертинг.** Без цифр нельзя ни выбрать следующий шаг, ни доказать бизнесу, что стало лучше. Мониторинг почти целиком делает DevOps-инженер, он не отнимает время у разработчиков. Алерты по DLX, длине очереди расчётов и времени заказа в статусе показывают зависшие заказы раньше, чем клиент пожалуется, и частично заменяют трейсинг и контроль сроков этапов.

Остальные инициативы в тройку не вошли. Дашборд MES заметно ускорится после выноса расчёта, а скорость работы операторов не ограничивает производство. Шлюз не увеличивает пропускную способность, а защиту заказов магазина от наплыва частично дают приоритеты очереди расчётов. Трейсинг и логирование дороже мониторинга, потому что требуют доработки всех трёх систем, при этом мониторинг и сверка уже показывают зависшие заказы. Автоматизация тестирования и отказоустойчивость важны, но напрямую не устраняют ни одну из причин, по которым компания теряет заказы.

Ожидаемый результат через полгода:

- потерянных сообщений нет: каждое либо обработано, либо лежит в DLX, и дежурный получил оповещение. Расхождения между MES и CRM сверка находит в течение часа;
- 95% заказов получают расчёт стоимости не позже чем через час после оформления;
- срок выполнения заказа снова укладывается в три недели;
- о зависших заказах компания узнаёт из алертов, а не из жалоб клиентов.
